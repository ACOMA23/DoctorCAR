## 1. التعريف بالمشروع وحالة الوظائف

DoctorCAR مشروع مراقبة وتسجيل وتشخيص سياقي، يجمع برنامج سطح مكتب عربيًا باستخدام Python/PySide6 مع مشروع جهاز ESP32-S3 مستقل. الهدف تسجيل ظروف الحدث وتحليل الأدلة المتاحة بدل الاكتفاء بإظهار رقم آني أو اسم رمز عطل.

قارئ OBD-II التقليدي قد يتيح بيانات حية وDTC وECU Freeze Frame بحسب دعم المركبة والمحول. أما نافذة DoctorCAR فهي تسجيل ينشئه البرنامج من **العينات التي استقبلها** قبل الحدث وبعده. ليست ECU Freeze Frame، ولا تستبدله، ولا تسترجع بيانات لم تصل أصلًا. **M1 لا يقرأ سيارة ولا يسترجع Freeze Frame من ECU.**

| الحالة | المقصود هنا | الوظائف الحالية |
| --- | --- | --- |
| Implemented | يوجد تنفيذ واختبار محلي للسلوك المحدد | محاكاة طبيعية/حقن/عشوائية، تاريخ جهاز برمجي، فحص المصادر، Replay، أحداث وSQLite، واجهة AR/EN وLight/Dark |
| Partial | تنفيذ موجود مع عيوب أو نقص قبول | تحقق غلاف استقبال Firmware وبناؤه وتشغيله الفعلي؛ A07 مفتوح، A01..A06 مصححة |
| Planned | لم ينفذ في M1 | ML في M2، XAI في M3، الكتالوج الميكانيكي الموسع، OBD/ISO-TP وCAN وMicroSD والتكامل الكهربائي |
| Not Tested | لا دليل تشغيل فعلي في البيئة المستهدفة | بناء Firmware وUSB مع لوحة ESP32-S3، الاتصال بمركبة، CAN/MicroSD وقياس جهد عتادي |

المحاكاة تمر ببدء المحرك والإحماء والخمول والتسارع والسير والتباطؤ والتوقف، وتتيح ارتفاعًا حراريًا تجريبيًا وقراءة غير منطقية وانقطاع قراءة. كل قيمها تحمل `SIMULATION`. هي نموذج تشغيل مبسط، وليست محاكاة فيزيائية معتمدة لسيارة محددة. كود الجهاز يولد `DEVICE_TEST`، وهي بيانات اختبار أيضًا.

## 2. متطلبات التشغيل والاعتماديات

مصدر التصريحات هو [desktop/pyproject.toml](desktop/pyproject.toml)، والإصدارات الدقيقة المسجلة في [requirements-lock.txt](desktop/requirements-lock.txt). ملف lock يستعمل **constraints مع `-c`**؛ لا يستبدل تثبيت حزمة المشروع.

| المكوّن | النطاق المصرح به | الإصدار في بيئة التدقيق |
| --- | --- | --- |
| DoctorCAR | `0.1.0`، Python `>=3.11` | Python `3.14.6` على Windows 11 build 26200 |
| PySide6 | `>=6.8,<7` | `6.12.0` |
| pyserial | `>=3.5,<4` | `3.5` |
| jsonschema | `>=4.23,<5` | `4.26.0` |
| pytest — dev | `>=8,<10` | `9.2.0` |
| Ruff — dev | `>=0.11,<1` | `0.17.3` |
| mypy — dev | `>=1.15,<2` | `1.20.2` |
| types-pyserial / types-jsonschema — dev | `>=3.5` / `>=4.23` | `3.5.0.20260712` / `4.26.0.20261006` |
| setuptools — build | `>=77` | أداة بناء معزولة يطلبها pip؛ ليست خدمة تشغيل |
| SQLite/logging/dataclasses/typing | مكتبة Python القياسية | لا تثبيت SQLite منفصل |

**النظام المختبر هو Windows فقط.** لا يوجد دليل قبول Linux أو macOS؛ وجود مكتبات متعددة المنصات لا يثبت تشغيل المشروع عليهما. Python 3.11 حد المشروع المعلن، وليس إصدارًا اختُبر هنا. metadata الخاصة بـPySide6 المثبتة تقيد Python إلى `>=3.10,<3.16`؛ التقاطع مع متطلبات المشروع يبدأ من 3.11، مع ضرورة توفر Wheel مناسب لنظامك ومعماريتك. تعتمد الواجهة على Qt Widgets/Core/Gui وبيئة رسومية وخط يدعم العربية. راجع [إعداد Qt for Python الرسمي](https://doc.qt.io/qtforpython-6/gettingstarted.html) عند تعذر تثبيت PySide6.

اختبارات Python تحتاج extra باسم `dev`. اختبارات Qt السلوكية تستخدم `offscreen` افتراضيًا؛ لا يعادل ذلك اختبار العرض الأصلي أو كل إعدادات DPI. لم تظهر الخطوط بشكل صحيح في offscreen في هذه البيئة، واستُخدم محرك Windows الأصلي لمراجعة الصور.

الاتصال التسلسلي يحتاج جهاز DoctorCAR التجريبي المحمل ببرنامج مناسب، وكابل بيانات ومنفذ COM معروف وغير مشغول. pyserial لا يثبت تعريف USB الخاص باللوحة. منفذ النقل يفتح بطلب صريح، بإعداد `115200` وقراءة غير حاجبة `timeout=0`؛ لا يكتشف التطبيق المنافذ تلقائيًا ولا يدعم محول OBD حقيقيًا في M1.

Firmware يستهدف ESP32-S3 DevKitC-1 وESP-IDF **5.5.x**، وراجعت واجهاته سابقًا مقابل **v5.5.1**. هذا هدف تطوير غير مثبت باختبار بناء. الأدوات `idf.py` وCMake وNinja لم تكن متاحة في PATH في تدقيق القبول. لا تحتاج لوحة أو ESP-IDF لتشغيل المحاكاة على الكمبيوتر. لا توجد تبعيات NumPy/Pandas/scikit-learn/SHAP في تثبيت M1 الحالي.

## 3. تثبيت تطبيق الكمبيوتر

ابدأ من نسخة محلية تحتوي [desktop/pyproject.toml](desktop/pyproject.toml). المسار التالي هو مسار هذا المشروع؛ عدله إذا وضعت نسختك في مكان آخر. لا يوجد عنوان مستودع بعيد موثق لافتراض أمر clone معين.

### 3.1 إنشاء البيئة وتفعيلها

```powershell
Set-Location C:\doccar
python --version
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

إذا كان Python متاحًا باسم `py` فقط، يمكن استخدام `py -3 -m venv .venv` بعد التحقق من إصداره؛ هذا بديل إرشادي لم يُستخدم في فحص هذا التحديث. تفعيل البيئة اختياري عند استعمال المسار الكامل للمفسر كما في الأوامر التالية. لا يلزم تغيير ExecutionPolicy للنظام؛ إذا حُظر التفعيل، استخدم المفسر مباشرة.

### 3.2 تثبيت حزمة المطور

```powershell
.\.venv\Scripts\python.exe -m pip install -c desktop/requirements-lock.txt -e './desktop[dev]'
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -c 'import doctorcar, PySide6, serial, jsonschema; print(doctorcar.__version__); print(doctorcar.__file__)'
```

الخيار `-e` يربط التثبيت بمصادر `desktop/src`؛ و`[dev]` يضيف أدوات الاختبار والأنواع. اعتماديات التشغيل منفصلة في pyproject ولا يوجد خادم أو قاعدة PostgreSQL أو Docker مطلوب. ينشئ pip ملفات تثبيت وmetadata؛ الأوامر هنا للمطور عند الإعداد، ولم يُنفذ تثبيت جديد أثناء مهمة تحديث README.

يوثق [سجل التدقيق للتثبيت](docs/evidence/acceptance-audit/package.log) نجاح تثبيت Wheel في بيئة جديدة، ومطابقته للمصدر وتشغيل Qt منها. أعيد في مهمة التوثيق فقط فحص الاستيراد و`pip check` والتفعيل، دون تثبيت مكتبات أو إعادة بناء الحزمة. لا تستخدم الحزم المثبتة عالميًا بديلًا عن بيئة المشروع.

للخروج من البيئة المفعلة:

```powershell
deactivate
```

## 4. تشغيل البرنامج والمصادر

### 4.1 الواجهة الرئيسية والتخزين

**شاشة البدء (DC-UX-001):** عند `python -m doctorcar` تظهر نافذة تحميل في أقل من نصف ثانية تعرض المراحل التي تُنفَّذ فعلًا فقط: تهيئة التطبيق، تحميل الإعدادات، تجهيز قاعدة البيانات، تحميل نموذج الذكاء الاصطناعي (خيط مستقل يتحقق من بصمة النموذج ويسخّن استيراد scikit-learn)، إعداد الواجهة. الشريط غير محدد (لا نسب مئوية وهمية). تُغلق الشاشة عندما تصبح النافذة الرئيسية قابلة للاستخدام (≈2 ث). فشل تحميل ML لا يمنع التشغيل (القواعد والتسجيل يعملان)؛ تعذر فتح قاعدة البيانات يعرض رسالة ودّية مع خيار «اختيار ملف آخر» أو الإغلاق؛ المهلة 30 ث. للتجاوز: `--no-splash` أو المتغير `DOCTORCAR_NO_SPLASH=1`.

```powershell
.\.venv\Scripts\python.exe -m doctorcar --no-splash   # بدون شاشة البدء
```

من جذر المشروع:

```powershell
.\.venv\Scripts\python.exe -m doctorcar
```

بعد تفعيل البيئة يتوفر أيضًا entrypoint باسم `doctorcar`، لكن مسار المفسر الكامل أوضح عند وجود أكثر من بيئة. خيار CLI الفعلي هو `--database`؛ لا توجد خيارات `--scenario` أو `--simulation` في CLI الواجهة.

```powershell
.\.venv\Scripts\python.exe -m doctorcar --database data/demo.sqlite3
.\.venv\Scripts\python.exe -m doctorcar --help
```

قاعدة البيانات الافتراضية هي `data/doctorcar.sqlite3` **نسبة إلى مجلد التشغيل الحالي**. ينشئ `SQLiteRepository` المجلد الأب والجداول تلقائيًا؛ قد توجد ملفات SQLite المرافقة `-wal` و`-shm` أثناء التشغيل. لتثبيت مكانها بصرف النظر عن مكان الطرفية، مرر مسارًا مطلقًا إلى `--database`.

### 4.2 تشغيل المحاكاة وإيقافها واستعادة التقرير

1. افتح **مركز المصادر** واختر **محاكاة — SIMULATION**.
2. اختر «رحلة طبيعية»، أو «ارتفاع حراري تجريبي»، أو «قراءة غير منطقية»، أو «انقطاع قراءة».
3. اختر سرعة العرض `1×` أو `10×` أو `30×` ثم اضغط **بدء الجلسة**. لا يبدأ مصدر تلقائيًا عند فتح التطبيق.
4. تنقل بين لوحة التحكم والحساسات والأحداث؛ الصفحات تستهلك الجلسة نفسها.
5. في السيناريو الحراري القياسي يظهر الكشف قرب الثانية 89 من زمن السيناريو؛ انتظر إلى ما بعد الثانية 119 لاكتمال نافذة ما بعد الحدث. هذه نتيجة السيناريو، وليست موعدًا لعطل مركبة أو ضمانًا زمنيًا على الحاسوب.
6. افتح **سجل الأحداث** وحدد الحدث ثم **عرض تقرير الحدث المحدد**، أو انقر الصف مرتين.
7. اضغط **إيقاف وحفظ المتاح** لإنهاء المصدر. التوقف قبل نهاية النافذة يحفظ الحدث `PARTIAL`.
8. أغلق التطبيق وافتحه بالأمر نفسه وبنفس `--database`؛ تستعاد قائمة الأحداث دون تشغيل المحاكاة. اختر الحدث لعرض التقرير من التخزين.

المحاكاة تولد عينة كل `200ms` من زمن السيناريو ولمدة `155000ms` افتراضيًا. التسريع يقلل الانتظار بين القراءات ولا يغير طوابعها الزمنية أو نافذة التسجيل؛ السرعة الفعلية تتأثر بالحمل والتخزين.

### 4.3 Replay مقابل ملف بروتوكول الجهاز

- **Replay:** من مركز المصادر صدّر الجلسة الحالية بزر **تصدير الجلسة لـ Replay** إلى ملف `.jsonl`، ثم أوقف المصدر واختر **إعادة تشغيل ملف — REPLAY** وافتح الملف. يحتوي هذا النوع على كائنات `Sample`، لا أغلفة HELLO/SAMPLE. يمنح Replay جلسة عرض جديدة ويحفظ `provenance` والأصل. الملف يجب أن يحتوي جلسة أصلية واحدة وبترتيب صالح. إعلان الدعم مشتق من حالة القراءات الفعلية؛ A01 مصحح.
- **ملف البروتوكول:** يولده محاكي الجهاز التالي، ويحتوي أغلفة رسائل البروتوكول. اختر **محاكي الجهاز / ملف البروتوكول** ثم **اختيار ملف البيانات**؛ لا تختَر مصدر Replay لهذا الملف.

```powershell
.\.venv\Scripts\python.exe -m doctorcar.protocol.simulator --scenario thermal --seed 42 --output data/device-test.jsonl
.\.venv\Scripts\python.exe -m doctorcar.protocol.simulator --help
```

إضافة `--pace` تجعل المولد يكتب تدريجيًا مع انتظار 0.2 ثانية عند SAMPLE؛ الملف نفسه ليس قناة اتصال حية في الواجهة، ويُفضل إكمال توليده قبل فتحه، لأن EOF ينهي `ProtocolFileSource`. يدعم المولد الخيارات `normal` و`thermal` و`invalid` و`dropout`. هويته `doctorcar-software-simulator` ومصدره `SIMULATION`.

### 4.4 جهاز الاختبار التسلسلي

عند توفر الجهاز وإذن استخدامه، اختر **جهاز DoctorCAR تجريبي — USB Serial**، وأدخل المنفذ الصحيح مثل `COM3` ثم ابدأ. لا تستخدم محول سيارة هنا. ينتظر التطبيق HELLO/CAPABILITIES، ويتوقف بخطأ إذا لم تكتمل المصافحة أو لم تصل بيانات خلال 10 ثوانٍ وفق شروط المصدر. لا توجد إعادة فتح تلقائية؛ أعد البدء صراحة بعد حل السبب. الاتصال الفيزيائي لم يختبر.

عولج A06: فشل التصدير المحلي يبقي الجلسة السليمة عاملة ولا يولد CONNECTION. أحداث الاتصال تظل بيانات نقل، ولا تثبت عطلًا ميكانيكيًا.

<a id="dc-cr-002"></a>
### 4.5 تحديث DC-CR-002: المحاكاة والتاريخ وفحص الاتصال والإعدادات

من جذر المشروع شغّل ` .\.venv\Scripts\python.exe -m doctorcar `، ثم افتح **مركز المصادر**. لا يبدأ مصدر تلقائيًا؛ أوقف الجلسة قبل تغييره. العناصر المخفية لا تدخل في وسيطات المصدر الجديد.

| الوضع | خطوات الواجهة | السلوك الفعلي |
| --- | --- | --- |
| NORMAL | محاكاة → رحلة طبيعية → بدء الجلسة | نموذج الرحلة المترابط نفسه، دون حقن |
| FAULT_INJECTION | محاكاة → حقن أعطال محددة → اختر عنصرًا أو أكثر، ثم البداية والمدة والشدة | يطبق التغييرات على الإشارات؛ يرفض تداخل أعطال تكتب الحساس نفسه |
| RANDOM_FAULTS | محاكاة → أعطال عشوائية كل 30 ثانية → Seed والحد الأقصى واحتمال الدورة الطبيعية | دورات عند 30/60/90/120/150 ثانية افتراضيًا، كل دورة طبيعية أو 1–3 أعطال متوافقة |
| Legacy | سيناريو M1 السابق → الحراري/غير المنطقي/الانقطاع | توافق مع سيناريوهات M1 وCLI القديمة |

**تجربة خلل مفاجئ:** اختر `thermal_sudden` «ارتفاع حرارة مفاجئ»، بداية **60 ثانية**، مدة **5 ثوانٍ**، شدة **1.0**، وسرعة **30×**. يعود المحاكي إلى الحرارة الأساسية عند 65 ثانية. قاعدة M1 تكشف الارتفاع بعد استمراره ثلاث ثوانٍ، أي **T=63s**؛ يستمر التسجيل حتى **93s** ويحتفظ بالنافذة **33..93s**، 301 عينة عند 200ms. انتظر اكتمال التسجيل وافتح تقرير الحدث من السجل؛ إيقاف المصدر مبكرًا ينتج PARTIAL موصوفًا.

| معرف الخلل | الإشارة/النمط | كشف M1 المتاح |

التعارض يرفض قبل بدء الجلسة، مثل thermal_sudden مع sensor_dropout في الوقت نفسه. يمكن جمع الحرارة والجهد وMAF لأنها تكتب إشارات مختلفة. حقول البداية والمدة والشدة في الواجهة مشتركة للأعطال المختارة؛ كل تعريف في `sources/faults.py` يحدد وصفه وحساساته ودليله المتوقع ومدته الافتراضية وقواعد الدمج. النطاق 0.1..1 للشدة و1..60 ثانية للمدة. المدة الافتراضية للأنماط التدريجية 20s والمتقطعة 12s في المجدول، وبقية الأنماط 5s؛ الواجهة تسمح بتغيير المدة المشتركة.

**Seed** مع الإعدادات ونسخة `fault-schedule-1` يحدد جدول الحقن والقراءات؛ سرعة العرض تؤثر في الانتظار الفعلي فقط. أُثبت التطابق عبر الواجهة عند 10× و30×. يحتفظ جدول `simulation_runs` في SQLite نفسها بـSeed والنمط وخطوة الزمن والمدة وmax_faults واحتمال الدورة الطبيعية والجدول والدورات. لوحة التحكم تعرض Injected/Detected/Not detected وأحداثًا بلا تطابق؛ المقارنة اللاحقة تطابق نوع القاعدة وزمن الكشف داخل الحقن. ليست قياسًا للدقة التشخيصية أو إثباتًا سببيًا، وقد تسجل خللًا للعرض بوصفه غير مكتشف لعدم وجود قاعدة له. لا تصل هويات الأعطال أو Ground Truth إلى detector أو hypothesis/evidence/report.

**التاريخ:** اختر **ذاكرة جهاز محاكاة — SIMULATED DEVICE HISTORY** ثم ابدأ. يتولد حدثان لجلسات اصطناعية سابقة بهويات ثابتة لـSeed نفسه: حرارة عند T=63s وجودة بيانات عند T=60s، بنافذتين كاملتين 30s قبل/بعد وبخطوة 1s. يستعمل التوليد `EventRecorder` الموجود ثم `HELLO/CAPABILITIES/EVENT_START/CHUNK/END` عبر codec/receiver وSession وSQLite نفسها، وبعد الرفع تبدأ جلسة حية طبيعية مستقلة. يظهر الأصل `LIVE` أو `HISTORICAL` أو `REPLAY` في السجل، و`SIMULATED DEVICE HISTORY` في provenance. الإيقاف ثم الاتصال بـSeed نفسه يعيد الحدثين دون تكرار. لا توجد ذاكرة ESP32 أو قراءة MicroSD فعلية؛ التاريخ مولد برمجيًا، وأوقاته نسبية لجلساته وليست توقيت عطل مركبة حقيقيًا. انقطاع التجميع يتطلب رفعًا كاملًا جديدًا؛ لا resume جزئي.

**فحص المصدر:** زر **فحص المصدر / الاتصال** يفحص إعدادات المحاكاة أو بنية Replay ووحداته وتسلسله، أو تأطير/إصدار/schema ملف البروتوكول ثم مصافحة كاملة على نحو منفصل. ملف HELLO فقط قد يكون سليم البنية مع مصافحة غير مكتملة. USB يعرض تحديث المنافذ وفحصًا بطلب المستخدم فقط: Port Available → Connecting → Handshake Pending → HELLO/CAPABILITIES → Connected → Receiving Data، أو Timeout/Protocol Error/Connection Lost. الحد 10s؛ يفتح الفحص المنفذ مرة واحدة ويغلقه في النجاح والفشل، ويحتاج بدء الجلسة طلبًا مستقلًا. تظهر هوية الجهاز وإصدارات Firmware/JSONL وتدفق العينات والقدرات المعلنة. نجاح الفحص لا يعني اتصال مركبة؛ الاختبارات الحالية بمنافذ وهمية فقط. لا تُرسل أوامر عبر Serial. أخطاء التصدير/التقرير المحلية تظهر للمستخدم وتبقي المصدر السليم عاملًا.

**الإعدادات:** اختر العربية AR أو English EN، وفاتح Light أو داكن Dark. العربية RTL والإنجليزية LTR مع حفظ اتجاه الحقول التقنية. تُحفظ اللغة والمظهر وSeed عبر QSettings في ملف `.settings.ini` بجوار قاعدة البيانات، وتُستعاد عند فتح القاعدة نفسها. System mode غير منفذ. التقرير الإنجليزي يعرض هوية الحدث وملخص الأدلة بالإنجليزية ويحافظ على النص التشخيصي العربي والفرضيات الأصلية تحت تسمية صريحة؛ لا يترجم السجلات التاريخية أو يعدل معناها في SQLite. الواجهة والأزرار والحالات مترجمة، والتقرير القديم يبقى مطابقًا بعد إعادة الفتح.

**أدلة التغيير:** [JUnit النهائي](docs/evidence/dc-cr-002/final.xml)، [السجل](docs/evidence/dc-cr-002/final.log)، [تجربة Qt](docs/evidence/dc-cr-002/e2e.json)، [صور Dark/English](docs/evidence/dc-cr-002/settings-en-dark.png)، [التاريخ](docs/evidence/dc-cr-002/history-ar-light.png). مصفوفة AT-001..015 والأوامر والقيود في [ملف التحكم](docs/DOCTORCAR_PROJECT_CONTROL.md). تعليمات الأقسام التالية محدثة؛ أدلة acceptance-audit القديمة تحفظ نتيجة 71/6 التاريخية.

### 4.6 DC-CR-003: سيناريوهات مترابطة وتشخيص قائم على الأدلة

من **مركز المصادر → محاكاة → عائلة المحاكاة: سيناريوهات مترابطة متعددة القياسات** اختر NORMAL أو حقنًا محددًا أو أعطالًا عشوائية. العائلة السابقة متاحة كما كانت للتوافق، وكذلك Replay والتاريخ وUSB وإعدادات AR/EN وLight/Dark. هذه نماذج تشغيل مبسطة وليست محاكاة فيزيائية معتمدة أو بيانات مركبة فعلية.

**تجربة عملية:** اختر «حقن أعطال محددة»، وفعّل **S02**، بداية60s، مدة35s، شدة1، وسرعة30×. افتح السجل ثم تقرير `MS_AIR_FUEL` بعد اكتماله. التجربة المسجلة كشفت عند **66s** واحتفظت بـ**36..96s / 301 عينة**. أدلة الكشف خلال58..66s: انحراف MAF عن مرجعه **−13.8163%**، وانحراف MAP **+4.0730kPa**، ومتوسط STFT **12.0549%**. يعرض التقرير احتمال هواء غير مقاس وبدائل انحراف القياس/قصور الوقود، ويقترح اختبار تسرب وفحص الأنابيب ومقارنة MAF/MAP والتصحيحات. لا يستنتج قطعة تالفة أو يؤكد التسرب.

في الوضع العشوائي تبدأ دورة عند30/60/90/120/150s افتراضيًا؛ قد تكون طبيعية أو تضيف حتى سيناريوهين متوافقين، بمدد5/18/45s وشدات0.6/0.85/1.0. المدة45s تعبر حد الدورة. يسمح بتداخل كتابات مختلفة مثل S01+S02، ويرفض الكتابة المتعارضة لنفس القياس مثل S02+S03. التطبيق مرتب وحتمي بالـSeed والإعدادات ونسخة `correlated-schedule-1`؛ لا يعيد بدء المسجل عند دورة جديدة. تحفظ `simulation_runs` الموجودة الجدول والدورات والملف العام للمعايرة؛ لا قاعدة أو Recorder جديدين.

**القواعد ليست أسماء السيناريوهات:** يتلقى `EventDetector` قياسات فقط، ويحسب نافذة آخر8s. جميع العينات الطبيعية والمضطربة للعائلة الجديدة تحمل معرف المعايرة العام نفسه `DOCTORCAR_CORRELATED_MODEL_1`؛ لا يحمل هوية السيناريو أو شدته أو جدوله. تستخدم القواعد هذا المعرف لحصر صلاحية حدود النموذج، ويحفظه Replay. تغيير أسماء السيناريوهات في phase/raw لا يغير نتيجة الكشف. البيانات التي لا تعلن هذه المعايرة تستمر بالقواعد القديمة؛ لا تطبق علاقات النموذج تلقائيًا على سيارة أو Firmware اختبار قديم.

مرجع الهواء المعلن: `MAF_expected = RPM × (0.002 + 0.00008 × load)`، و`MAP_expected = 30 + 0.65 × load`. الانحراف محسوب من القراءات الفعلية مقابل هذين المرجعين. الحدود اختيارات هندسية لفصل أمثلة التطوير الطبيعية والمضطربة، وليست حدود مصنع أو نتيجة معايرة إحصائية على سيارات. تحتاج القاعدة≥3 عينات صالحة تمتد≥1s، بفجوات≤1.5s ووحدات السجل، وآخر عينة صالحة للمراجع المطلوبة. تستثني STALE/UNSUPPORTED/INVALID/MISSING للمراجع؛ MS_SIGNAL يسمح بفقد/فساد الهدف فقط. معدل الاختبار200ms أو1s؛ لا ادعاء ملاءمة أي معدل أو تزامن OBD فعلي.

التصنيف التشخيصي **مشتق ومنفصل عن Quality**: NORMAL، ABNORMAL_OPERATION، IMPLAUSIBLE_SIGNAL، SIGNAL_LOSS_OR_SUSPECTED_FLATLINE أو UNRESOLVED. قراءة AVAILABLE قد تكون غير متسقة سياقيًا؛ وثبات MAP مع مراجع ثابتة لا يكفي لاتهام الحساس. لا يُعاد تصنيف جودة العينة أو تغيير سجلها المخزن لتلائم التشخيص.

التقرير الجديد يعرض A..K: الأعراض، إحصاءات القياسات ووحداتها وأوقاتها، العلاقات، النظام المحتمل، الفرضيات، أدلتها الداعمة والمعارضة المتاحة، النواقص، الفحوص، القيود، والنافذة. إحصاءات B تخص كامل نافذة الحدث؛ أدلة C تحسب حتى **لحظة الكشف فقط** دون استعمال المستقبل. عدد الأدلة في السجل هو عدد المقاييس الكمية المعروضة، ولا يعني استقلالها أو نسبة ثقة. يستمر المسجل حتىT+30 حتى لو اختفى الخلل أو بدأت دورة جديدة. تبقى تقارير الأحداث القديمة متوافقة، وواجهة التقرير الجديدة تدعم AR/EN.

لوحة المحاكاة تفصل «المجدول/المحقون» عن «ما اكتشفه DoctorCAR». المقارنة اللاحقة تتطلب نوع نمط متوقعًا مع أدلة كمية فعلية؛ الحدث بلا أدلة لا يُحسب نجاحًا. يسمح تطابق الزمن بذاكرة القاعدة8s بعد انتهاء الحقن. تظهر الحالات غير المكتشفة والأحداث غير المتطابقة وإنذارات الفترات الطبيعية؛ نهاية المشاهدة المبكرة CENSORED، وQuality أحداث مرافقة لا إثبات صحة تشخيص. جدول Ground Truth لا يدخل Evidence/Hypotheses/Report أو الكاشف.

**التقييم الفعلي:** كُشفت الأنماط المتوقعة في **16/21** حالة مجدولة:7/7 أمثلة تطوير و9/14 تنويعات معلمات. لم تظهر إنذارات في3 رحلات طبيعية، ولم تسجل أحداث أنماط غير متطابقة في هذه المجموعة. ليست هذه دقة تشخيص ميكانيكي أو اختبار تعميم مستقل. الحالات الخمس غير المكتشفة: S01/S02/S04/S05 عند55s/9s/شدة0.65، وS07-flatline عند80s/20s/0.9؛ الحالة الأخيرة لا توفر تغير المراجع الكافي. المدد والشدة القصيرة قد لا تحقق حدود الأدلة؛ لم تُخفَ هذه الحالات أو تضبط القواعد لضمان كشفها.

العربية وRTL منطق عرض، والأرقام السالبة والوحدات والمعرفات تستخدم عزل LTR عند الحاجة. قيم طور Firmware مثل `TEST_IDLE` معرفات تقنية قادمة من المصدر وليست ترجمة آلية. [لقطة تقرير من تدقيق القبول](docs/evidence/acceptance-audit/e2e-report-after-restart.png) دليل تاريخي للواجهة الأصلية، لا صورة جديدة أنتجتها مهمة التوثيق.

<a id="pipeline"></a>
## 6. المعمارية ومسار البيانات الفعلي

ترتيب التنفيذ يستخرج من [Session.step](desktop/src/doctorcar/core/session.py)، وليس من شكل الهيكل المقترح:

```text
DataSource.read_measurements()
  → Session.step()
  → DataQualityValidator.validate_measurement()
  → SQLiteRepository.save_session() + save_measurement()
  → EventDetector.evaluate_trigger()
  → EventRecorder.append_measurement()
      → TimeRingBuffer.append_measurement()
      → استكمال أحداث نشطة / start_event() / finalize_event()
      → SQLiteRepository.save_event() وربط العينات
  → BackendWorker.snapshot / events_changed
  → MainWindow: العرض الحي والسجل

طلب عرض تقرير
  → worker command: report
  → SQLiteRepository.get_event()
  → build_evidence() → evaluate_hypotheses() → build_diagnostic_report()
  → report_ready → MainWindow.show_report()
```

`ValidationResult.accepted=false` يمنع دخول العينة المكررة أو المتراجعة إلى المسار الحي. العينات المقبولة تُحفظ كلها، لا عينات الأحداث فقط، ولذلك يمكن تصدير الجلسة. `DataQualityValidator` ينشئ نسخة مطبعة مع `raw` ولا يستبدل غياب القياس بصفر.

للأحداث المرفوعة مسار داخل `Session.step` نفسه: `source.drain_events()` ثم تحقق جودة عيناتها ثم `save_event()`؛ لا يعاد تشغيل الكاشف على كل حدث مستورد. يتولى `ProtocolReceiver` قبل ذلك تجميع الأجزاء وفحصها. دمج حدث مرفوع مع العينات الحية نفسها مثبت بعد إصلاح A05؛ اختلاف قياس فعلي يظل تعارضًا مرفوضًا.

خيط `BackendWorker` الواحد يملك المصدر وSession ووصلة SQLite. أوامر الواجهة تدخل `queue.Queue(maxsize=32)`؛ الإشارات تعيد النتائج إلى Qt. تحديث العرض محدود إلى نحو مرة كل 120ms في حلقة العامل، وليس لكل رسالة حتمًا. إغلاق النافذة يطلب shutdown ويؤجل الإغلاق حتى ينتهي العامل؛ لا يستدعي I/O المركبة أو القرص داخل خيط GUI. لا يوجد Backend أو خادم مستقل أو Session Manager ثانٍ. ويُفعَّل مسار AI (`AnomalyAnalyzer`) اختياريًا من الواجهة داخل `Session` نفسها دون Session أو مسجل ثانٍ؛ وفشله لا يوقف القواعد (انظر القسم 10).

## 7. سجل الحساسات وجودة القراءات

السجل الوحيد هو `REGISTRY: SensorRegistry` و`SensorSpec` في [sensor_registry.py](desktop/src/doctorcar/core/sensor_registry.py). يحتوي كل تعريف على `sensor_id` والاسم العربي و`variable` و`unit` و`kind` و`source` و`valid_range` و`missing_policy`. نطاق الصلاحية العام `None` حاليًا؛ لا توجد مواصفة مركبة موثوقة مضمنة. `get_supported_sensors()` يرشح حسب مجموعة دعم يمررها المستدعي، ولا يكتشف مركبة من تلقاء نفسه.

| المعرف | الاسم العربي | المتغير | الوحدة | النوع |
| --- | --- | --- | --- | --- |
| RPM | دوران المحرك | rpm | rpm | direct |
| SPEED | سرعة المركبة | speed | km/h | direct |
| COOLANT_TEMP | حرارة سائل التبريد | coolant_temp | °C | direct |
| ENGINE_LOAD | حمل المحرك | engine_load | % | direct |
| THROTTLE_POS | موضع الخانق | throttle_pos | % | direct |
| INTAKE_PRESSURE | ضغط هواء السحب | intake_pressure | kPa | direct |
| MAF | تدفق الهواء | maf | g/s | direct |
| INTAKE_TEMP | حرارة هواء السحب | intake_temp | °C | direct |
| SHORT_FUEL_TRIM | تصحيح الوقود القصير | short_fuel_trim | % | direct |
| LONG_FUEL_TRIM | تصحيح الوقود الطويل | long_fuel_trim | % | direct |
| CONTROL_MODULE_VOLTAGE | جهد وحدة التحكم | control_module_voltage | V | direct |
| DTC | رموز الأعطال | dtcs | بلا وحدة رقمية | diagnostic، مجموعة معلومات وليست حساسًا مستقلاً |

المحاكي يولد القراءات الرقمية كلها ويعلنها مع DTC. جهاز الاختبار في المصدر C يعلن القائمة نفسها. إعلان دعم مصدر اختبار لا يثبت دعمها في أي سيارة. Replay يستمد الدعم من القراءات غير UNSUPPORTED في البيانات المقروءة؛ الفحص الكامل يستعرض الملف دون إبقاء المقبض مفتوحًا. مستقبل البروتوكول يحول الحساس غير المعلن إلى `UNSUPPORTED` ويحتفظ بغيابه صريحًا.

| Quality | تمثيل ومعنى |
| --- | --- |
| AVAILABLE | قيمة رقمية متاحة؛ لا تعني سلامة القطعة |
| MISSING | قراءة غائبة أو `null`؛ لا تعامل كصفر |
| UNSUPPORTED | المصدر لا يدعم القراءة؛ القيمة المطَبَّعة `null` |
| INVALID | وحدة خاطئة أو قيمة خارج حدود plausibility التجريبية أو جودة غير صالحة |
| STALE | عمر يتجاوز 3000ms عند توفر ساعة مصدر مناسبة؛ ليس تشخيصًا لعطل كهربائي |

يتحقق `Reading` من الرقم المحدود ويرفض bool وNaN وInfinity كقيم. يتحقق validator من التسلسل والتوقيت والفجوات والوحدات والغياب والعمر. حدود المحاكاة الواسعة مطبقة حاليًا على RPM وSPEED والحرارة والحمل والخانق والجهد فقط؛ ليست قواعد صلاحية لجميع القراءات أو السيارات، ولا يكتشف كل شذوذ ممكن. Replay يحتفظ بزمن العينات ويعمل دون فرض عمر ساعة المضيف على سجل قديم.

DTC مخزنة منفصلة في `Sample.dtcs` مع `dtc_quality`؛ عدم وجود رمز ضمن بيانات متاحة مختلف عن عدم دعم DTC. `freeze_frame` حقل اختياري مستقل وغير متاح من مصادر M1 المنفذة. قائمة **80 عاملًا** و**68 فرضية** أهداف بحثية غير معتمدة، وليست 80 حساسًا مدعومًا أو 68 عطلًا مشخصًا.

## 8. اكتشاف الأحداث والتسجيل الزمني

`Session.start()` يربط المصدر ويبدأ القراءة؛ كل عينة مقبولة تذهب إلى التخزين والمراقبة. لا يلزم زر مستقل لبدء مسجل الحدث.

### 8.1 القواعد السابقة المستمرة للتوافق

`EventDetector.evaluate_trigger()` يستخدم `demo-rules-1.0`:

- `THERMAL_DEMO`: للعائلة السابقة؛ في سياق SIMULATION أو DEVICE_TEST أو Replay ذي provenance تجريبية، حرارة صالحة `>=108°C` وRPM صالحة `>400`، مع مرور `3000ms` منذ بدء شرط الحرارة وفق عينات التقييم. هذه شروط نموذج اختبار فقط؛ لا معيار عام لكل السيارات. يعود الكاشف للاستعداد عندما لا يتحقق شرط hot.
- `DATA_QUALITY`: عند وجود `issues` من validator؛ يمنع latch إعادة الإطلاق ما دامت issues مستمرة ويعيد الاستعداد بعد زوالها. لا يحول القراءة الثابتة وحدها إلى عطل.
- `CONNECTION`: ينشئه `Session.record_connection_loss()` عند استدعائه من معالجة الخطأ في العامل. ليست قاعدة استنتاج كهرباء سيارة. يفصل العامل أخطاء الملفات المحلية عن فقد النقل بعد إصلاح A06.

DTC ليس شرطًا لهذه القواعد. لا توجد عشرات قواعد القطع أو مصنف ميكانيكي مدرب.

### 8.2 النافذة والتداخل

1. `TimeRingBuffer.append_measurement()` يحتفظ بآخر `30000ms` بحسب `timestamp_ms`، مع حدود شاملة؛ لا يفترض أن 30 ثانية تساوي عددًا ثابتًا من الصفوف.
2. `EventRecorder.append_measurement()` يضيف العينة للمخزن ويستكمل الأحداث النشطة. `start_event()` يأخذ المتاح من `get_pre_event_window()` ويسجل trigger ونسخة القاعدة وسببها وأدلتها.
3. يستمر ضم العينات حتى `trigger.timestamp_ms + 30000`. إذا تجاوزت عينة لاحقة النهاية، لا تضم خارج النافذة ويُنهي المسجل الحدث بالمتاح. غياب عينات قرب حد النافذة لا يعوض بقراءات مختلقة.
4. يحتفظ المسجل بأول trigger من النوع نفسه داخل حدث نشط؛ لا ينشئ حدثًا مطابقًا أو يمدد النهاية تلقائيًا. يمكن لأنواع مختلفة أن تتداخل وتشترك في صفوف measurements عبر event_samples.
5. معرف الحدث UUID5 مشتق من الجلسة والنوع ووقت الكشف. قاعدة SQLite تمنع تكرار event_id وتمنع overwrite متعارضًا لحدث نهائي. دمج الرفع والعينات الحية مثبت محليًا بعد إصلاح A05.
6. `finalize_event()` يحدد `end_ms` لآخر عينة محفوظة وحالة COMPLETE أو PARTIAL. `stop()` يحفظ الأحداث التي لم يكتمل بعدها 30 ثانية كجزئية. إذا لم تتوفر 30 ثانية قبل الحدث، يضيف limitation يصف ذلك.

تثبت الأحداث تدريجيًا في SQLite. عند توقف سابق غير نظامي، يحول `recover_interrupted()` آخر checkpoint من RECORDING إلى PARTIAL مع شرح؛ لا يستعيد عينات لم تُكتب. في التجربة المسجلة عند 5Hz حُفظت **301 عينة** من 59s إلى 119s حول كشف 89s؛ وعند 1Hz تكون النافذة نفسها 61 عينة.

معدل الوصول والحمل والفجوات يحدّون من التفاصيل؛ لا ضمان لالتقاط تغير أسرع من معدل وصول العينات، ولا إثبات لاستمرار حالة أثناء فجوة بلا قياسات. أُصلح A04؛ تبقى العينات المقبولة المعلقة عند HELLO لجلسة جديدة، مع عزل كل جلسة عن الأخرى. الطوابير محدودة وتعلن الامتلاء؛ لا ضمان فقد صفري في كل الظروف.

## 9. التشخيص والأدلة والتقرير

| المستوى | التنفيذ الحالي والمعنى |
| --- | --- |
| Observation | وصف ما رُصد أو ما سجله trigger، مثل ارتفاع حراري تجريبي أو نقص بيانات |
| Anomaly | تحقق قاعدة تجريبية أو إخفاق جودة؛ ليست دلالة سببية على قطعة |
| Evidence | عينات ووحدات وجودة ومصدر ونسخة قاعدة وDTC المتاحة وحدود النافذة |
| Hypothesis | احتمال يحتاج تحققًا مستقلًا، مع بيانات ناقصة وفحص مقترح |
| Limitation | سياق تجريبي، غياب مواصفات المركبة أو القياس المستقل أو Freeze Frame، جزئية النافذة |

`build_evidence()` يحسب أعلى حرارة من القراءات AVAILABLE فقط، ويجمع DTC المتاحة وعدد القراءات غير المتاحة وحالة Freeze Frame والمصدر والنافذة. `evaluate_hypotheses()` لا يصنف قطعًا: للحدث الحراري ذي حرارة صالحة يعرض احتمال حالة حرارية/تبريد تحتاج فحصًا واحتمال انحراف قياس بديلًا؛ ولـCONNECTION يعرض مسار النقل دون اتهام كهرباء السيارة؛ وفي غير ذلك يصرح بنقص الأدلة. أضاف CR003 إحصاءات كل قراءة وعلاقات نافذة سابقة للكشف وتصنيفًا مشتقًا؛ تقرير A..K للعائلة المعايرة الجديدة كما في4.6.

نموذج `Hypothesis` يحتوي supporting_evidence وcontradicting_evidence وmissing_evidence وrecommended_check، مع حقول عرض EN مضافة بتوافق خلفي. القواعد متعددة القياسات تبني فرضيات متعددة، وتعرض الأدلة المعارضة المتاحة والنواقص والفحوص؛ لا يوجد محرك ترجيح سببي أو scoring ميكانيكي معاير. لا يستنتج النظام سلامة قطعة من قراءة واحدة أو تلف مضخة/ثرموستات من الحرارة وحدها.

`build_diagnostic_report()` ينشئ نصًا عربيًا به هوية الحدث والمصدر وحالة التسجيل والملاحظة والسبب ونسخة القاعدة ووقت الكشف والأدلة والأسباب المحتملة والبيانات الناقصة والفحص وحدود النتيجة. لا ينتج PDF أو نسب ثقة ميكانيكية. لا توجد مكتبة تشخيص شاملة أو قائمة 68 حالة منفذة. التوقيت النهائي المستورد يتحقق من مطابقته لآخر عينة وعدم سبقه الكشف بعد إصلاح A03. الأوامر المحلية لا تتحول إلى CONNECTION بعد إصلاح A06. يقبل العرض language="en" مع إبقاء النص التشخيصي العربي الأصلي.

| التقنية | الحالة (DC-CR-005) | ما هو موجود فعليًا | القيود |
| --- | --- | --- | --- |
| IoT / تكامل الجهاز | VERIFIED على TCP loopback وملف ومنفذ وهمي؛ **NOT TESTED** على لوحة | JSONL v1، محاكي جهاز برمجي (`protocol/network_simulator.py`)، `NetworkDeviceSource` (127.0.0.1 فقط)، رفع تاريخي idempotent، إعادة اتصال محدودة | لا Wi-Fi/LAN/Cloud، ولا اتصال مركبة؛ الجهاز الشبكي محاكاة |
| كشف الشذوذ متعدد القياسات (ML) | IMPLEMENTED + VERIFIED في المحاكاة | `analysis/`: نوافذ 5s بخطوة 1s و47 ميزة، IsolationForest، سياسة استمرارية (v2: 5 نوافذ متتالية)، نموذجان محزومان: **v2 الافتراضي** و v1 | استدعاء ML وحده 0.10؛ القواعد هي المصدر الرئيسي للكشف؛ لا إثبات على مركبات |

| التشخيص الميكانيكي | IMPLEMENTED (قواعد MS_* + فرضيات) | `monitoring/evidence_rules.py`, `diagnostics/` | بلا ثقة معايرة ولا كتالوج 80/68 |

**فصل الطبقات:** ML يعطي درجة شذوذ؛ XAI يشرح درجة النموذج فقط؛ التشخيص الميكانيكي يعرض فرضيات وفحوصًا من قواعد القياسات؛ العارض يترجمها. كشف الشذوذ ليس إثباتًا لتلف قطعة، ولا يُستخدم اسم العطل المحقون في أي استدلال.

### 10.1 كيف يُربط تحليل AI بالحدث

لكل نتيجة AI وقت بداية ونهاية نافذة. عند إنشاء حدث عند الزمن T يُربط **آخر** تحليل `end_ms ≤ T` من الجلسة نفسها بشرط ألا يزيد عمره عن ضعف إزاحة النافذة (2000ms)، وتُسجل حالة في الجدول الإضافي `event_ai_status`. لا يُربط تحليل مستقبلي ولا من جلسة أخرى ولا من نموذج مختلف عما سُجل. تحليل ANOMALOUS لاحق خلال 10s يُربط منفصلًا ويُعرض في التقرير بوصفه «لاحقًا». الحالات: `ANALYZED_NORMAL`، `ANALYZED_ANOMALOUS`، `INSUFFICIENT_DATA`، `MODEL_NOT_LOADED`، `INFERENCE_FAILED`، `DISABLED`، `HISTORICAL`، `NO_RECENT_ANALYSIS`، `NOT_RECORDED` (أحداث أقدم). التحليل الطبيعي لا يحوّل حدث القواعد إلى «اكتشفه AI».

### 10.2 النماذج وإعادة التدريب والتقييم

## 11. تطوير Firmware ودورة الجهاز

مشروع [firmware](firmware/CMakeLists.txt) مستقل عن Python، بلغة C وESP-IDF. نقطة البداية `app_main()` في [main.c](firmware/main/main.c). يوجد كود وظيفي، لكن وصفه التالي قراءة للمصدر، وليس شهادة بناء أو تشغيل جهاز.

### 11.1 التهيئة والدورة

- يتحقق المصدر من ESP32-S3 ومن حد أدنى لـESP-IDF `5.5.0`، بينما الهدف الموثق 5.5.x. لا يعني غياب guard أعلى إثبات التوافق مع SDK أحدث.
- `usb_serial_jtag_driver_install()` يهيئ TX بحجم 8192 وRX بحجم 4096. قناة JSONL هي USB Serial/JTAG الأصلية؛ console على UART وفق sdkconfig.defaults، مع تعطيل console الثانوي.
- تقرأ هوية المصنع عبر `esp_efuse_mac_get_default()` لتكوين device_id؛ ويضاف رقمان من `esp_random()` لتكوين session_id عند boot. لا يوجد تخزين معرف جلسة في SD أو قاعدة بيانات على الجهاز.
- يستخدم `esp_timer_get_time()` كأساس نسبي، وFreeRTOS `vTaskDelay(10ms)` في الحلقة. يرسل SAMPLE كل نحو 200ms، وHEARTBEAT كل نحو 1000ms، وHELLO/CAPABILITIES كل نحو 5000ms لإتاحة الالتحاق وسط التشغيل.
- `dc_test_sample()` يحسب بيانات مترابطة من موضع الزمن في دورة 155 ثانية؛ زمن الرسالة وتسلسل العينة يستمران ولا يعادان للصفر عند تكرار السيناريو. خيار `CONFIG_DOCTORCAR_TEST_THERMAL` يضيف الارتفاع الحراري.
- `dc_send()` يضيف غلاف v1 و`DEVICE_TEST` ويطبع cJSON دون تنسيق مع LF، ويرفض ما يتجاوز 4096 بايت. توجد محاولات إرسال محدودة وسجل تحذير عند إرسال ناقص؛ تسلسل الرسائل مستقل عن تسلسل SAMPLE.

### 11.2 الأخطاء والنطاق

`dc_poll_input()` يقرأ أجزاء 128 بايت دون انتظار طويل، ويجمع السطر في buffer محدود. `handle_line()` يقبل HELLO لإعادة الإعلان وACK دون إجراء، ويولد ERROR للخطأ الأساسي أو النوع غير المدعوم. **تحقق C لا يطبق جميع الحقول الإلزامية كما يفعل Python؛ هذه A07.** بعض أخطاء التخصيص ترجع false/NULL، وأخطاء تهيئة رئيسية تمر عبر ESP_ERROR_CHECK. لا تعادل هذه المعالجة اختبار تحمل ذاكرة أو فقد طاقة على جهاز.

`DOCTORCAR_REAL_CAN_ENABLED=0` وحارس التجميع يمنع تفعيله في هذا المصدر. لا يوجد TWAI أو ISO-TP أو MicroSD أو ADC أو RTC منفذ. لا تغير هذا الحارس لتعلن دعم CAN؛ ذلك يتطلب تنفيذًا واختبارات وهاردوير محميًا في نطاق منفصل.

| العتاد أو الاسم | صلته بالتنفيذ الحالي |
| --- | --- |
| ESP32-S3 DevKitC-1 | اللوحة المستهدفة؛ لا دليل تشغيل فعلي عليها في هذا المشروع بعد |
| transceiver CAN خارجي / MCP2562FD | حاجة مستقبلية/اسم طرح في التكليف؛ لا driver أو توصيل محدد له في الكود. transceiver ليس OBD interpreter ولا يضيف CAN FD إلى TWAI الداخلي |
| MicroSD عبر SPI | هدف M5؛ لا تهيئة SPI/FATFS أو حفظ محلي منفذ |
| ADS1115 | لا تعريف أو driver أو قياس عتادي مرتبط به في المشروع الحالي؛ جهد العينات قيمة اختبار، لا ADC سيارة |
| DS3231 | لا driver أو مزامنة RTC منفذة؛ timestamp الحالي نسبي، لا تاريخ حادث مأخوذ من هذه القطعة |

لا تفترض وجود هذه القطع أو اعتماد اختيارها الكهربائي. TWAI المستهدف لاحقًا Classical CAN، وقراءة OBD تحتاج طبقة تشخيص وISO-TP عند الحاجة. القياس الكهربائي والحماية والتغذية والسكون وفقد الطاقة أهداف لاحقة، لا قدرات معلنة للجهاز الحالي.

## 12. تثبيت ESP-IDF والبناء والبرمجة

**كل أوامر ESP-IDF التالية إرشادية ولم تنفذ في بيئة المشروع؛ لا SDK متاح في PATH ولا اختبار لوحة مسجل. لم يُنفذ Flash أثناء كتابة هذا الدليل.**

### 12.1 تثبيت الأدوات على Windows

استخدم [دليل Windows الرسمي لـESP-IDF v5.5.1 / ESP32-S3](https://docs.espressif.com/projects/esp-idf/en/v5.5.1/esp32s3/get-started/windows-setup.html). نزّل مثبت Espressif المرتبط منه، واختر الإصدار المستهدف 5.5.x، ويفضل 5.5.1 لمطابقة مراجعة API. يجهز المثبت Python وأدوات البناء والمترجم؛ لا تخلط بيئة Python الخاصة بالتطبيق مع بيئة SDK. افتح اختصار **ESP-IDF PowerShell Environment** الذي يجهزه المثبت. اختر مسار تثبيت ASCII قصيرًا بلا مسافات وفق قيود الدليل؛ لا حاجة لنسخ مشروع مثال فوق firmware الحالي.

### 12.2 التحقق والبناء فقط

من طرفية ESP-IDF، لا من بيئة تطبيق سطح المكتب:

```powershell
idf.py --version
Set-Location C:\doccar\firmware
idf.py set-target esp32s3
idf.py menuconfig
idf.py build
```

`menuconfig` اختياري لمراجعة DoctorCAR M1 test data وخيار السيناريو الحراري. `set-target` يعيد توليد تكوين البناء وقد يعيد ضبط إعدادات بناء سابقة؛ لا تكرره بلا حاجة بعد تخصيصها. الجذر CMake يرفض هدفًا غير s3، وmain/CMakeLists.txt يطلب مكونات json وUSB/timer/hardware support. لا تعالج فشل البناء بإعلان النجاح من وجود ملفات C فقط. مرجع سلوك الأوامر: [idf.py الرسمي v5.5.1](https://docs.espressif.com/projects/esp-idf/en/v5.5.1/esp32s3/api-guides/tools/idf-py.html).

### 12.3 Flash ومراقبة الجهاز — بعد توفر اللوحة وموافقة صريحة فقط

الأسماء COM3 وCOM4 أمثلة يجب استبدالها بالمنافذ الفعلية. إغلاق قارئ آخر للمنفذ ضروري قبل استخدامه. الأمر الأول يبرمج اللوحة؛ لا يدخل ضمن فحوص التوثيق أو بناء الكمبيوتر:

```powershell
$flashPort = 'COM3'
idf.py -p $flashPort flash
```

للسجلات الداخلية افتح **منفذ UART console المناسب**، الذي قد يختلف عن منفذ USB Serial/JTAG الخاص بالبيانات:

```powershell
$consolePort = 'COM4'
idf.py -p $consolePort monitor
```

لمراقبة بيانات JSONL افتح مصدر USB Serial التجريبي في تطبيق DoctorCAR على منفذ **USB الأصلي** المناسب، لا منفذ console. تحقق من HELLO بإصدار `0.1.0-test` و`test_mode=true`، ومن CAPABILITIES مع `can=false` و`microsd=false` و`event_upload=false`، ومن SAMPLE ذات `DEVICE_TEST` وتسلسل وزمن متزايدين وقراءات متغيرة. هذا إجراء تحقق مستقبلي، لا نتيجة اختبار موجودة. لا تفتح التطبيق وmonitor على المنفذ نفسه في الوقت نفسه. توثيق الواجهات ليس تصريحًا بتوصيل المركبة.

<a id="protocol"></a>
## 13. بروتوكول الاتصال وأمثلة الرسائل

العقد الفعلي هو [device_protocol_v1.schema.json داخل الحزمة](desktop/src/doctorcar/protocol/device_protocol_v1.schema.json). مدخل [schemas/device_protocol_v1.schema.json](schemas/device_protocol_v1.schema.json) يشير إليه محليًا بـ`$ref`، ولا يمثل عقدًا ثانيًا. يحمّل `codec.py` المخطط من package resources ويستعمل `Draft202012Validator`. تفاصيل إضافية في [DEVICE_PROTOCOL.md](docs/DEVICE_PROTOCOL.md)، مع أولوية عيوب القبول الحديثة عند وصف ما يعمل.

### 13.1 التأطير والحقول المشتركة

UTF-8، كائن JSON واحد في كل سطر، وLF نهائي، وحد **4096 بايت شامل LF**. يفحص `decode_message()` الطول والتأطير وUTF-8 وJSON والنسخة والمخطط، ويرفض المفاتيح المكررة والثوابت غير المحدودة. لا تضف حقولًا عليا غير معرفة بالمخطط.

| الحقل المشترك الإلزامي | المعنى والقيد |
| --- | --- |
| protocol_version | العدد الصحيح `1`؛ النسخ الأخرى مرفوضة في codec |
| type | واحد من الأنواع التسعة أدناه |
| device_id / session_id | نص غير فارغ حتى 128 حرفًا؛ هوية جهاز وجلسة/boot |
| sequence_number | عدد صحيح غير سالب لكل **رسالة**، ويشمل heartbeat والمصافحة |
| timestamp_ms | عدد صحيح غير سالب، زمن نسبي للجلسة وليس UTC |
| source | SIMULATION أو DEVICE_TEST أو REPLAY؛ لا REAL في M1 |
| payload | object ببنية النوع المحدد |
| event_id | إلزامي إضافي لرسائل EVENT_START/CHUNK/END |

للـSAMPLE تسلسل مستقل داخل `payload.sample.sequence_number`؛ لا يستعمل ترتيب الرسائل بدل ترتيب العينات. يجب أن تطابق session/source/timestamp داخل العينة الغلاف. `sample_version` وsession/source/sequence/timestamp/readings حقول العينة الإلزامية؛ `dtcs` و`dtc_quality` وphase وreceived_at_ms وdevice_id وprovenance وfreeze_frame وraw حقول إضافية معرفة. كل reading لها value رقم محدود أو null وunit وquality. يضيف مستقبل الكمبيوتر وقت استقباله وهوية الجهاز ويحتفظ بالغلاف الخام.

### 13.2 حالة تنفيذ أنواع الرسائل

| النوع | الغرض وحقول payload الإلزامية | الكمبيوتر/المحاكي البرمجي | Firmware الحالي بالقراءة، غير مختبر |
| --- | --- | --- | --- |
| HELLO | firmware_version، test_mode=true؛ تعريف جهاز اختبار | إنشاء/تحقق ومصافحة قبل البيانات | يرسل دوريًا وعند HELLO واردة؛ تحقق الإدخال ناقص A07 |
| CAPABILITIES | sensors، can=false، microsd=false، event_upload | يحفظ قائمة الدعم ويتحقق من القراءات المعلنة | يرسل 12 معرفًا وevent_upload=false |
| SAMPLE | sample؛ عينة v1 | يفكها إلى Sample ويطبق التحقق المشترك | يولد بيانات اختبار فعلية حسابيًا؛ لا CAN |
| HEARTBEAT | uptime_ms؛ متابعة الجهاز | يفك الغلاف ويحدث ساعة المصدر؛ لا يولد قراءة حساس | يرسل كل نحو ثانية |
| EVENT_START | total_chunks، total_bytes، sha256 | يهيئ تجميع حدث نهائي | لا يرسل أحداثًا مجزأة في M1 |
| EVENT_CHUNK | index، data بصيغة Base64، sha256 | يفحص الجزء ويخزنه حتى اكتمال التجميع | غير منفذ كرفع أحداث |
| EVENT_END | sha256 | يتحقق من الحدث المجمع ويخرجه عبر drain_events | غير منفذ كرفع أحداث |
| ACK | ack_sequence | codec يعرفه؛ receiver لا يطبق عليه إجراء خاصًا، والتطبيق لا يرسله تلقائيًا | يهمله دون تغيير هاردوير |
| ERROR | code، message | يحوله إلى خطأ ظاهر للمصدر | يرسله للأخطاء الأساسية أو الرسائل غير المدعومة |

`device_messages()` يولد HELLO/CAPABILITIES/SAMPLE/HEARTBEAT بـSIMULATION. `event_messages()` يبني رسائل الرفع لاختبار Python؛ CLI محاكي الجهاز لا يرفع تلقائيًا أحداثًا مكتشفة ولا يكتب ACK. معرفة النوع في schema لا تثبت أن الجهاز ينفذه.

### 13.3 أمثلة JSONL صحيحة للعقد

الأمثلة التالية **بيانات توثيق اختبارية مولدة من حقول المخطط والدوال، وليست مخرجات لوحة أو مركبة**. تعرض كل كتلة سطر JSON واحدًا؛ عند النقل يلحقه LF. الهوية `doctorcar-doc-test` متعمدة لتمييزها عن الجهاز الفعلي. إعلان RPM وDTC فقط مثال لقدرات محدودة، لا قائمة Firmware الحقيقية.

**HELLO — تعريف نسخة ووضع اختبار:**

```json
{"protocol_version":1,"type":"HELLO","device_id":"doctorcar-doc-test","session_id":"doc-session-1","sequence_number":0,"timestamp_ms":1000,"source":"DEVICE_TEST","payload":{"firmware_version":"doc-example","test_mode":true}}
```

**CAPABILITIES — دعم معلن قبل البيانات:**

```json
{"protocol_version":1,"type":"CAPABILITIES","device_id":"doctorcar-doc-test","session_id":"doc-session-1","sequence_number":1,"timestamp_ms":1000,"source":"DEVICE_TEST","payload":{"sensors":["RPM","DTC"],"can":false,"microsd":false,"event_upload":true}}
```

**SAMPLE — RPM مع DTC منفصلة؛ تسلسل الرسالة 2 وتسلسل العينة 0:**

```json
{"protocol_version":1,"type":"SAMPLE","device_id":"doctorcar-doc-test","session_id":"doc-session-1","sequence_number":2,"timestamp_ms":1000,"source":"DEVICE_TEST","payload":{"sample":{"sample_version":1,"session_id":"doc-session-1","source":"DEVICE_TEST","sequence_number":0,"timestamp_ms":1000,"readings":{"RPM":{"value":800,"unit":"rpm","quality":"AVAILABLE"}},"dtcs":[],"dtc_quality":"AVAILABLE","phase":"TEST_IDLE"}}}
```

**HEARTBEAT — عمر الجهاز النسبي:**

```json
{"protocol_version":1,"type":"HEARTBEAT","device_id":"doctorcar-doc-test","session_id":"doc-session-1","sequence_number":3,"timestamp_ms":1000,"source":"DEVICE_TEST","payload":{"uptime_ms":1000}}
```

**EVENT_START — حدث توثيقي جزئي في جزء واحد:** المحتوى المفكوك للجزء التالي كائن Event v1 حجمه **567 بايت**؛ status=PARTIAL، وفيه العينة السابقة وسبب توثيقي وlimitation بأن النافذة ناقصة. ليس مثالًا على اكتمال 30 ثانية قبل/بعد.

```json
{"protocol_version":1,"type":"EVENT_START","device_id":"doctorcar-doc-test","session_id":"doc-session-1","sequence_number":4,"timestamp_ms":1000,"source":"DEVICE_TEST","payload":{"total_chunks":1,"total_bytes":567,"sha256":"da9e31bf0564444bd7cdaf8acf82cbca9ebc25e6b32fb55d78ace25f3d1de330"},"event_id":"doc-event-1"}
```

تمثل هذه الأمثلة عقدًا صالحًا وفحص تجميع. اختبارات القبول تثبت الآن حفظ SAMPLE ثم EVENT لنفس العينة دون تصادم بيانات استقبال المضيف بعد إصلاح A05. ERROR الأخيرة يفترض أن تظهر كخطأ. مثال ACK لا يعني أن الكمبيوتر أرسله إلى الجهاز أو أن له أثر تحكم.

### 13.4 التحقق والتكرار وإعادة الاتصال

- `ProtocolReceiver.feed()` يجمع الشظايا، ويرفض السطر الكبير ويستأنف التأطير بعد LF مع تسجيل خطأ. queues محدودة: 512 عينة و8 أحداث مكتملة و100 رسالة خطأ.
- المصافحة HELLO ثم CAPABILITIES مطلوبة قبل البيانات؛ تطابق الهوية والمصدر مفروض. التسلسل المتكرر أو المتراجع لا يعيد العينة، والفجوة تعد وتسجل. تحتفظ instance المستقبل بآخر watermarks لما يصل إلى 32 هوية جلسة؛ ليست سجلًا دائمًا بعد إغلاق البرنامج.
- الحدث حتى 2MiB، وبحد أقصى 4096 جزءًا و4 تجميعات نشطة. الجزء المفكوك حتى 1024 بايت وBase64 حتى 1400 حرف؛ مولد `event_messages` يستعمل 768 بايت للجزء. يفحص SHA256 لكل جزء ولكامل الحدث، والحجم والفهرس والهوية والجلسة والمصدر والحالة النهائية.
- يقبل الجزء المكرر نفسه إذا وصل برقم رسالة جديد، ويرفض محتوى متعارضًا. ينتهي التجميع غير المكتمل بعد 60 ثانية عند معالجة رسائل أحداث، أو عند reset_connection. هذا ليس مؤقت انتهاء يعمل أثناء الصمت المطلق.
- بعد إعادة الاتصال تعاد المصافحة والرفع كاملًا من EVENT_START؛ لا resume جزئي أو ACK-driven retry آلي. برنامج الكمبيوتر لا يعيد فتح منفذ مفقود تلقائيًا، وينتظر إعلان Firmware الدوري عند البدء.
- عولج A04 بحفظ العينات المقبولة المعلقة عند HELLO لجلسة جديدة. عولج A05 بمقارنة القياس الدلالي مع حفظ أول metadata استقبال ورفض تعارض القيم. يبقى A07 في تحقق غلاف C، ولا يوجد ضمان تشغيل جهاز فعلي.
- SHA256 فحص سلامة نقل، لا مصادقة جهاز أو تشفير. السجلات الداخلية منفصلة عن JSONL. `ProtocolFileSource` يرفض EOF مبتورًا أو حدثًا ناقصًا؛ `SerialDeviceSource` يوقف الجلسة عند خطأ ظاهر بدل تقديم قراءات جديدة مختلقة.

## 16. SQLite والحفظ والاستعادة

المخطط التالي مستخرج من SQL داخل [sqlite_repository.py](desktop/src/doctorcar/storage/sqlite_repository.py). ينشأ في constructor عند فتح المسار. كل connection تبقى في الخيط الذي أنشأها.

| الجدول | الأعمدة الفعلية | المفاتيح والعلاقات |
| --- | --- | --- |
| sessions | session_id، source، started_at_ms، status | session_id PK؛ مصدر واحد لكل جلسة |
| measurements | session_id، sequence_number، timestamp_ms، data_json | PK(session_id,sequence_number)، وsession_id FK إلى sessions |
| events | event_id، session_id، trigger_ms، kind، status، metadata_json | event_id PK، وsession_id FK؛ metadata تحتوي trigger/version/evidence/end/limitations |
| event_samples | event_id، session_id، sequence_number | PK للأعمدة الثلاثة؛ FK إلى events وFK مركب إلى measurements |
| simulation_runs | session_id، metadata_json | PK/FK إلى sessions؛ Seed/إعدادات/نسخة وجدول الحقن ودوراته |

يحفظ data_json العينة المطَبَّعة والمصدر والوحدات والجودة وraw/provenance. لا يكرر metadata_json قائمة العينات؛ تعيد `get_event()` تكوينها بربط event_samples وترتيبها زمنيًا. `list_events()` يعيد ملخصات السجل، و`export_session()` يكتب صفوف الجلسة بالترتيب إلى JSONL.

يفعل المخزن `foreign_keys=ON` و`journal_mode=WAL` و`synchronous=FULL`، ويستعمل معاملات وSQL parameters. `PRAGMA user_version=2` هو الإصدار الحالي؛ يقبل 0 و1 و2، ويضيف simulation_runs إلى القاعدة نفسها مع حفظ الجداول والسجلات السابقة. يرفض إصدارًا مستقبليًا غير معروف. لا يوجد مدير ترحيل أو قاعدة ثانية.

`save_event()` يتجنب تكرار هوية الحدث النهائي إذا كان مطابقًا، ويرفض استبداله بمحتوى مختلف. يشارك الحدث عينات موجودة بمفاتيحها؛ تُستثنى received_at_ms وraw وdevice_id فقط من مقارنة التكافؤ، مع حفظ أول metadata استقبال، وتبقى القيم والتوقيت والجودة والمصدر وprovenance ملزمة. أي تعارض قياس يرفض؛ هذا يصلح A05 دون كتابة فوق القياس الأول.

عند الإيقاف النظامي تصبح الجلسة STOPPED، والأحداث غير المكتملة PARTIAL. عند الفتح بعد توقف سابق تتحول RECORDING إلى PARTIAL مع آخر عينة وشرح الاستعادة، وACTIVE إلى INTERRUPTED. `started_at_ms` وقت المضيف عند الحفظ وليس زمن حدوث عطل؛ زمن القياس الأساسي نسبي للجلسة. لا يضمن WAL أو checkpoint عينات لم تصل أو معاملة لم تكتمل قبل فقد الطاقة.

لا تشغّل نسختين مسجلتين على SQLite نفسها؛ لا قفل متعدد التطبيقات في M1. أغلق البرنامج بصورة سليمة قبل نقل ملفه؛ ملفات WAL قد تكون جزءًا من الحالة أثناء التشغيل. افحص قاعدة موجودة دون إنشائها إذا غابت، من الجذر:

```powershell
.\.venv\Scripts\python.exe -c 'import sqlite3; c=sqlite3.connect("file:data/doctorcar.sqlite3?mode=ro", uri=True); print(c.execute("PRAGMA table_info(events)").fetchall()); c.close()'
```

المسار الافتراضي يظل `data/doctorcar.sqlite3` نسبة إلى مكان تشغيل CLI؛ ملفات تجارب scripts/audits مختلفة عنه كما في القسم التالي، ولا تظهر أحداث قاعدة تجربة تلقائيًا عند فتح قاعدة افتراضية أخرى.

أدلة acceptance-audit/ السابقة محفوظة وتصف **71/6 التاريخية**؛ لا تمثل النتيجة الحالية. المحاولة الأولى لبرنامج تجربة CR توقفت بمهلة 40s لأن Replay يعمل افتراضيًا بالزمن العادي؛ حُفظ [سجلها](docs/evidence/dc-cr-002/e2e-attempt1.log). التجربة النهائية تتحقق من فحص الملف وتشغيل Replay وإيقافه صراحة، بينما اختبار التغيير test_at014_export_and_complete_replay_create_isolated_event يغطي مسار Replay الكامل. لا توجد إخفاقات منتج باقية في suite الحالية، ولا ادعاء تحقق جهاز فعلي.

<a id="safety"></a>
## 20. السلامة والقيود

- النموذج الأولي لم يثبت دقته التشخيصية على سيارات فعلية. SIMULATION وDEVICE_TEST بيانات اختبار صريحة؛ Replay إعادة تشغيل مع provenance، وليس مصدر قياس حي جديدًا.
- قراءة غير طبيعية أو DTC أو أعلى مساهمة تفسير مستقبلية لا تثبت تلف قطعة أو السبب الجذري. التشخيص يتوقف على جودة الأدلة والسياق والمواصفات والفحص الفاصل؛ لا نسب ثقة ميكانيكية معايرة في M1.
- OBD-II لا يتيح كل حساس أو خدمة في كل مركبة؛ يجب اكتشاف الدعم وتوثيق المصدر مستقبلًا. المراقبة السلبية لـCAN مختلفة عن طلبات التشخيص النشطة للقراءة؛ لا ينفذ M1 أيًا منهما على السيارة.
- توصيل ESP32 مباشرة بكهرباء السيارة أو بخطي CAN دون واجهة ومستويات وحماية وتغذية مناسبة غير آمن. لا يوثق هذا المشروع الحالي مخطط توصيل كهربائي معتمدًا أو توافق قطعة مع مركبة.
- مسح DTC وإعادة الضبط والكتابة والترميز وتشغيل المشغلات وبرمجة وحدات السيارة خارج النطاق. Flash في القسم 12 يخص لوحة التطوير فقط وبعد إذن مستقل؛ لا أمر تحكم سيارة في التطبيق أو المصدر الحالي.
- لا Cloud أو حسابات أو مفاتيح API مطلوبة. SHA256 للأجزاء ليس تشفيرًا أو تحقق هوية جهاز؛ لا تدّع أمن نقل لم ينفذ.
- لا ترفع المشروع أو بيانات جلسة لخدمة خارجية تلقائيًا. راجع تراخيص PySide6/Qt ومكوناتها قبل توزيع البرنامج؛ لم يعتمد قرار توزيع. python-OBD غير مستخدم كاعتماد للمشروع، وتحتاج مراجعته إن اختير لاحقًا.
- A01..A06 مصححة ومثبتة باختباراتها القديمة. A07 وبناء Firmware وتشغيل اللوحة قيود قبول باقية. فتح تطبيقين يسجلان على DB نفسها غير مدعوم.

## 21. خارطة الطريق

الحالات مستخرجة من [ملف التحكم الرئيسي](docs/DOCTORCAR_PROJECT_CONTROL.md)، وليست إذنًا ببدء تنفيذ لاحق:

| المرحلة | النطاق | الحالة الحالية |

| M1 — Functional Foundation & Simulation | desktop ومحاكاة وReplay وأحداث وتقارير وبروتوكول ومصدر Firmware test | **PARTIAL**؛ إصلاحات القبول مفتوحة، وbuild/العتاد غير مختبرين |
| M2 — Time-Series Anomaly Detection | بيانات ونوافذ وميزات ونموذج ومقارنة baseline ومنع تسرب | IMPLEMENTED + VERIFIED في المحاكاة (DC-CR-004/005)؛ قيمة مضافة فوق القواعد غير مثبتة |
| M3 — Explainable AI | تفسير نموذج متحقق وحدود مساهمة الميزات | IMPLEMENTED + VERIFIED (استبدال مرجعي، ليس SHAP) |

| M7 — Final Evaluation | دقة وقيمة إضافية وموثوقية وتراخيص وتسليم | Planned |

أُنجزت إصلاحات A01..A06 ضمن DC-CR-002 واجتازت الاختبارات. قبل اعتماد M1 كاملًا يبقى A07 وإثبات بناء Firmware ومخرجاته عند توفر SDK واللوحة وفي تكليف منفصل؛ لا بدء M2 أو تكامل هاردوير.

### سجل تحديث README السابق — تاريخي قبل DC-CR-002

نطاق هذه المهمة **README.md في الجذر فقط**. قُرئت المصادر والاختبارات وCMake والمخططات والأدوات والأدلة الفعلية، وتحقق غياب scenarios وanalytics بدل نسخ هيكل مخطط. الفحوص الجديدة الخفيفة كانت:
